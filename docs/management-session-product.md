# AgentCaptain · 队长：0.7 管理会话与产品边界

状态：**管理会话已实现，0.7 采用自动管理工作终端；桌面交接仍为实验性功能**。单元测试和无实机 UI 合同测试覆盖核心状态与权限；真实 Codex 初始化、供应商兼容性、桌面入口和长期恢复仍需要按具体安装版本验证。本文不把源代码完成或深链接打开当作实机验收通过。

产品主线是：**一个主控，统筹本机与远程 Agent。AgentCaptain 创建、初始化和恢复一条真实的本机 Codex 管理对话，由 Captain（队长）组织工作，工作 agent 完成实际工程任务**。用户保留最终决策权；主控负责理解目标、向相关工作 agent 澄清专业问题、拆解派发、跟进监督、协调依赖、核对送达与验收证据，再汇总结果和待决事项。AgentCaptain 不另建模型后端，不默认后台唤醒推理，也不改变 worker 的角色或增加隐藏汇报协议。

## 专家管理者的职责与任务级授权

主控不是只转发一句话的信使，也不是默认亲自执行各机器项目的工程师。它是当前领域的专家管理者：能判断目标、依赖、风险和证据是否充分；不知道的细节先问负责该项目的工作 agent，而不是猜测、要求用户代为解释，或直接用 SSH 越过工作 agent 改代码。仓库调查、规范确认、实现、测试、提交/PR 状态核验和实际工程交付由工作 agent 做，主控负责组织和审阅这些结果。worker 内部如何再分工不必展开成用户需要管理的另一层。

用户表达“让这个 agent 把适配和校验完善好”即授权主控在该目标范围内管理工作：读取相关最新输出、询问背景和权威依据、拆解/派发任务、补充约束、追问结果、指出差距并安排返工、核验送达和收集验收证据。无需为每一次相关询问或跟进重新请求同意。“只看看”“不要发任务”等明确限制仍优先；仅查询的请求不能被扩展为实现或外部修改授权。已登记开放终端自动可管理是连接策略，不是自动执行与用户目标无关的任务。

管理者可以在任务范围内与工作 agent 进行必要的多轮普通对话，但“管理和对话的一切权限”不等于可替用户输入秘密、批准工作 agent 的审批、变更模型供应商、创建未授权目录、终止不相关进程，或进行未获授权的破坏性/外部协调操作。目标扩大、在既定权威下仍无法解决的来源冲突、未获授权的不可逆操作或超出原任务的发布/PR 状态变更需要具体指出取舍并交给用户决定，不能把 worker 的建议当作新增用户授权。

默认使用管理工具读取与沟通，不因为本机还有 shell、SSH 或 GitHub 工具就替工作 agent 执行业务。如果没有合适的工作 agent，说明缺口；新建必须满足已明确设置的机器/项目目录与用户目标，不静默接管外部会话。只有用户明确要求修复 Hub/插件/连接平台时，当前执行者才切换为该平台的工程角色，在相应项目范围内实施维护；这不是管理业务项目时的默认替代路径。

### 一次目标的管理闭环

1. **定位责任对象。** 用已登记列表识别相关项目和专业领域，仅核对选定 agent；名称相同用机器、目录与准确 ID 消歧。不要为了一个项目遍历所有终端和历史。
2. **接续而非重发。** 先读该会话最新的真实输出和原任务送达记录，判断正在执行、已经报告还是存在未知送达。已有任务能继续就追问或补充，不把同一目标重新当成全新任务派发；不确定提交先查原 `request_key`。
3. **向专家补齐信息。** 若缺少背景、最新规范版本、失败复现或 PR 状态依据，直接向负责的 worker 提出具体问题。主控可以质疑结论、要求原始证据和复测；缺乏证据时不靠旧记忆填补技术事实。
4. **明确委派。** 用普通用户文本给出目标、范围、优先级、权威来源、保护现有工作的约束、期望交付物与验收条件。复杂任务可拆成几次相关对话，模型/执行工具/子 agent 的细节由工作 agent 处理。
5. **跟进与纠偏。** 核对送达后读新增结果；发现遗漏、规范冲突或未覆盖测试就补充、澄清或安排返工。只在确实超出原目标、需要人类审批或重要选择时向用户升级问题，不把每一步管理动作都推回用户。
6. **证据验收。** 让 worker 提供规范来源及准确版本/commit、变更摘要、测试命令与结果、失败/未跑项目、交付物或 PR 链接。主控审阅证据与目标是否一致，有疑点继续问负责 agent；只有证据满足验收条件才汇报为已验证完成。

“最新规范为权威”需要 worker 实际核对当前上游 revision，不能把用户对某修复已合入的预期当作已证实。指定 ASL/规格为权威时，以其语义核验适配；实现现状、旧报告和 PR 评论是辅助证据，不能反过来覆盖规范。闭环汇总说明使用的准确依据、实际测试、残余风险及需要用户决定的事项。

### 用户和 worker 的交互保持简单

用户可以随时在同一个工作终端直接对话。主控发送的也是正常任务/问题，不要求 worker 知道组织层级，不附加隐藏管理 协议、角色切换或特殊汇报标记，不伪造额外系统权限。主控从已有输出和持久化送达记录整理进展；不能以管理效率为理由覆盖人的草稿、绕过审批或抢占另一客户端。

业务进展与终端连接状态分开汇报：

| 业务阶段 | 所需证据与汇报含义 |
| --- | --- |
| `submitted`（已提交） | 持久化送达证明输入写入；尚不能声称已开始或完成 |
| `working`（进行中） | 关联会话的后续输出明确表明已接收并执行该任务；不是输入回显或仅 PTY 在线 |
| `reported`（结果待验收） | worker 给出结果，但规范、测试或交付证据尚不充分 |
| `verified`（已验证） | 目标与验收条件有对应的版本、结果/交付物和测试证据，未完成项单列 |
| `blocker`（阻塞） | 说明具体阻碍、已做检查、责任对象和下一步；需用户决定时给出明确问题 |

这些是管理汇报口径，不是宣称新增自动任务状态机。主控负责当前交互中的闭环管理；Hub 保存记录与事件，但不会自动唤醒模型、替用户持续定时执行或在管理对话空闲后自行启动下一轮推理。需要持续监测时使用用户明确要求的产品调度机制，不把“已派发”写成无人值守跟进已安排。

## 用户的主流程

首页上方是管理会话卡片，第一次显示「启动管理会话」，已有记录时显示「继续管理」。卡片展示名称、准确的状态/阶段、自动纳入的工作会话数量、当前输入入口和错误。准确 Session ID、工作区、终端 ID、工具握手和桌面验证情况放在高级信息中。

第一次只需要：

1. 使用默认名称「我的管理会话」，或自定义名称。
2. 已连接、已登记且未关闭的共享工作终端**自动纳入管理**，不再选择逐会话范围、激活或分配所有者。没有工作终端时也允许启动管理会话；后续连接的工作终端自动加入。不扫描全部机器或历史。
3. 可选地为「创建工作会话」授权已连接机器及具体项目目录，通过目录浏览器选择，不要求记住路径。默认不授权新建工作。
4. 在系统准备角色、工具与原生会话后，在真实管理终端中交流；必要的登录、信任与审批仍由用户完成。

普通流程不要求填写 Python 路径、MCP JSON、模型供应商或 Session ID。机器与工作终端页面仍保留，供配置连接和用户直接参与工作。工作会话可以改显示名称或置顶，便于跨机器区分；名称不替代精确会话和终端身份，也不修改 Codex 对话。管理终端使用独立记录、专用工作区和独立终端服务，不加入 worker 列表；打开管理视图、轮询或异步初始化完成不会抢走工作终端中的焦点和输入草稿。

产品默认一条管理会话。已有默认记录时，准备操作返回原记录，而不是静默生成第二个主控；新建工作终端的目录设置走独立管理设置接口。后端可表示不同管理身份，它们自动看到同一批有效工作终端，不通过 worker 所有权隔离访问；各自 capability、请求键和送达记录身份仍独立。UI 不把多管理者创建或层级管理作为已完成产品。

## 启动、身份与工具初始化

准备阶段在源码仓库外的用户私有状态目录创建工具拥有的管理工作区，写入专用 `AGENTS.md`、项目 `.codex/config.toml`；独立工具连接文件保留在私有运行目录。Windows 新建工作区使用 `%LOCALAPPDATA%/AgentCaptain/management-workspaces`，Linux/macOS 使用 XDG 用户状态目录中的 `agent-captain/management-workspaces`，避免目录信任扩大到整个源码仓库。已登记工作区保持原有准确路径，不随品牌更新搬迁；详见[改名与兼容说明](rebranding.md)。显式开发/测试 runtime 保持隔离在该命名空间内。不修改业务项目的指导文件，不覆盖用户全局 Codex 配置，不复制认证文件，也不改变用户原有模型、供应商和审批策略。首次目录信任必须由人确认，不能为完成验收而自动批准。

实际启动分两步：

1. 使用本机可信的 Codex 启动入口执行一次 `exec --json` 初始化，显式采用 `read-only` 沙箱和管理工作区。首轮只调用已认证的 `get_controller_context` 自检，然后简短说明自动管理工作终端和新建目录权限、等待用户任务；不读 worker 历史、不发任务、不新建 worker、不做业务工作。
2. 从该工具自己启动进程的原生身份事件取得准确 Session ID，保存身份并验证管理工具握手。随后在独立真实终端中用精确 ID `resume` 该对话，并重新提供同一管理者的工具连接。

身份来自受管原生启动事件，不来自模型自报、标题、PID、可见截图或目录中的最新文件。工具握手来自携带独立凭据的管理工具请求，不来自模型说“已连接”。初始化期间的 worker 操作由服务端状态限制，而不是只靠提示词约定。

「可对话」需要准确身份、工具已核验、以及终端前台可用。仅进程存在或 PTY 连接不够。登录、供应商配置、会话占用、工具失败和后台功能冲突都显示明确错误或「等待你确认」，不自动确认权限、删除锁、fork 或重启共享 daemon。配置尚未可用时，先由用户修复本机 Codex 的日常启动流程。

初始化会保存非秘密的启动程序 argv，后续精确恢复使用该入口，不因网页后台换了 PATH 而切换 CLI 版本。入口消失时停在环境错误，不尝试另一个模型客户端。初次只读自检允许最多十分钟，保持用户原 reasoning 设置；耗时不会触发第二个启动。

## 自动管理工作终端，保留身份与新建权限边界

管理者的身份来自独立 capability，不接受模型传入的 `controller_id` 冒充身份。管理 capability 必须有效，管理会话必须具备可信原生 Session、完成工具握手且不处于初始化、身份未知或已关闭阶段，才能操作工作对象。列举、读取、写入和事件都由服务端核对**已登记、开放、绑定真实共享终端且不是管理者**的工作对象；送达查询还校验请求所属管理身份，不能冒充其他管理者查取记录。这些是实际服务端边界，不只是提示词中的名单。

0.7 不再要求「激活」、逐 worker grant 或唯一管理所有者。有效工作终端自动进入管理列表，包括旧记录中 `active=false` 的终端和管理会话启动后新连接的终端。显示连接暂时断开但仍绑定原终端的工作对象继续保留，以便查询状态和按明确指令恢复原连接；断开不代表可以发送任务，也不意味着原模型进程已经结束。已关闭、正在关闭、关闭结果未知、仅有历史记录以及管理终端均不作为工作对象。

「创建工作会话」是另一项权限：仍校验机器连接和用户明确授予的 canonical 项目目录范围。自动管理已有终端不会增加主机、新目录或整机文件系统创建权限；默认没有新建目录授权。目录授权收紧不删除已有工作终端，也不会把已连接工作对象移出自动管理。业务文本不作为 shell 命令执行。

管理者与 worker 分离。服务端拒绝以 worker API 注册、读取、发送或创建管理者，也拒绝管理者工作区内的工作对象；不能管理自己或递归创建下位主控。自动管理不取消终端关闭、输入草稿、审批和用户直接操作的边界，不通过迁移重写已有工作终端或 Codex Session 身份。

这些隔离仅约束 **AgentCaptain APIs**，不是 Codex 所有原生工具、其他插件或 SSH 账号的系统权限。保留 Codex 自己的沙箱和人工审批；项目不是多租户网关或整机权限沙箱。

### 旧版已有对话插件的兼容边界

现有 Codex 对话安装本地插件后，同样使用有效共享工作终端的自动列表。兼容工具名 `list_active_agents` 保留，但不再表示必须先手工激活；它只列本服务登记的有效工作终端，不扫描机器或历史。`get_controller_context` 会明确返回现有插件的 `legacy` 身份模式或 Hub 管理会话的 `scoped` 身份模式；两者都声明 `worker_access: automatic`，不能把 `scoped` 误解为仍需勾选 worker。

从 Hub 创建的管理者不需要手动安装该插件：工作区和受管启动已配置工具。管理者保持独立身份和送达命名空间，现有插件仍使用其原有服务连接身份；这是单用户个人控制台，不宣传为多租户隔离。升级不会删除用户现有缓存、注销终端或改写供应商认证。

## 状态、幂等与生命周期

| 状态 | 页面含义与行为 |
| --- | --- |
| 尚未创建 | 启动管理会话，默认一个 |
| `prepared` | 初始化包已准备，等待启动 |
| `bootstrapping` / `initializing` | 执行原生初始化、核验准确身份与工具，不派发工作 |
| `attaching` | 恢复准确原 Session 的真实终端 |
| `needs_attention` | 登录、信任、权限、占用或启动提示需用户处理 |
| `ready` | 原生身份、管理工具及终端前台可用，用户可交代目标 |
| `disconnected` | 显示连接不可用，原身份保留，不据此认定任务结束 |
| `desktop_unverified` | Hub 输入已释放，准备同一会话链接；桌面接管未核验 |
| `failed` / `unknown` | 展示明确阶段与错误，核对原操作，不强制新建 |
| `closed` | 管理终端结束、工具身份停用，保存身份与历史用于明确恢复 |

准备、启动和恢复操作保持稳定请求键。浏览器 sessionStorage 保留当前启动操作，后端记录 prepare/start/resume 身份和结果；重复点击、刷新或响应丢失不会靠新键重复生成会话。原结果未知时先核查，不用“恢复”之名新建另一条原生对话，也不自动重新发送初始目标或业务任务。

正常终端按键与持久任务送达不同：UI 不为未知按键结果自动重发。工作任务继续使用已有持久送达查询与稳定 `request_key`；`submitted` 只证明写入，不证明模型接受、执行或验收完成。

升级到自动管理不是旧任务重发授权。迁移只在自有数据库中封存旧规则下尚未提交、原管理范围外或旧 inactive 目标的可重试插件请求，将其标为 `not_sent` 并保留说明；不会联系终端、启动模型、恢复会话或发送文本。已提交、结果未知、已撤销的请求保持原状态，新规则不会把它们重新变成可提交任务。今后的合法新任务仍需用户意图和新的稳定请求键，不能把更大的自动列表当作旧请求执行许可。

收起管理显示、切换工作终端或关闭浏览器，不发送草稿、不关闭管理进程、更不结束 worker。「结束管理会话」经明确确认后，只结束该管理入口、停用其能力；历史和准确 Session 仍保留。关闭 Python UI 服务与关闭独立终端 broker 不是同一动作：broker 或主控机器停止仍可能结束本机 PTY。

## Codex 桌面入口：实验性，不是已验证无缝交接

「在 Codex 中继续」用于打开**同一条已保存原生会话**，不是新建同名对话。MVP 先要求用户明确确认管理者空闲、终端没有未发送草稿，然后核对受管终端状态、释放 Hub 的输入入口，返回 `codex://threads/<exact-session-id>` 供用户点击。

此时记录 `input_owner=desktop`、`state=desktop_unverified`、`desktop_verified=false`。Hub 不再输入管理终端，旧入口中的在途输出响应不会覆盖新所有权状态。这里的“desktop”只是选择了桌面输入入口，**不是证明桌面实际取得会话控制权**。

打开链接不能证明桌面端成功接管、项目信任或管理身份 MCP 加载，也不能证明临时 CLI 配置与桌面模型/供应商一致。用户需核对；程序不悄悄同步全局设置或切换模型。持久项目配置和启动覆盖均已准备，但桌面加载规则仍需按安装版本实测。

返回 Hub 前先关闭另一客户端，再点击「继续管理」，使用准确原 ID 恢复，不重新初始化、不重发任务。会话仍被占用时保留明确错误，不 fork、删锁或盲目开第二个写者。

官方 CLI `/app` 路线可以作为后续验证的适配器候选，但 MVP 不自动将它输入终端。只有证明同一 Session、工具身份、输入所有权与失败恢复之后，才能宣称已验证的顺畅交接。[官方 CLI 命令说明](https://learn.chatgpt.com/docs/developer-commands)

## 已实现接口与模块

UI 管理 API 通过已有本机 cookie/Host/Origin 保护，不暴露给 scoped MCP 执行管理者的生命周期操作。

| 接口 | 作用 |
| --- | --- |
| `GET /api/controllers`、`GET /api/controllers/get` | 列举管理记录、核对状态 |
| `POST /api/controllers/prepare`、`start` | 准备角色/工具与可选新建目录设置，并启动原生只读初始化 |
| `POST /api/controllers/resume` | 精确恢复原管理会话，不重新初始化 |
| `POST /api/controllers/scope` | 管理设置：仅显式编辑新建工作终端的机器/项目目录授权 |
| `GET /api/controllers/output`、`POST input`、`resize` | 管理终端显示与用户输入，不经过 worker 登记 |
| `POST /api/controllers/desktop` | 明确确认后释放 Hub 入口，返回原 Session 链接 |
| `POST /api/controllers/close` | 明确结束管理入口，不关闭 worker |

`prepare` 和 `scope` 为旧客户端兼容仍接受 `agent_ids`，但该列表不参与有效工作访问判定，也不能缩减自动列表、分配唯一所有者或因列表变化撤销待送达任务。旧 worker-scope 表保留用于审计，不作为当前 grant；有效 `scope`、`scope_count`、`effective_worker_count` 都按当前有效登记工作终端动态计算。只提交 `agent_ids` 不会清空现有新建目录设置；明确提交 `allowed_hosts` 或 `host_roots` 才编辑这些创建权限。`worker_access: automatic` 说明当前策略；`scope_enforced_by_hub: true` 表示身份和有效工作对象边界仍由服务检查，不表示需要用户勾选会话。

管理记录与普通 agent 登记分开，保存准确 Session、专用工作区、终端身份、初始化/操作阶段、明确新建目录权限、工具状态和输入入口。连接凭据在私有 descriptor 中，数据库仅保存能力哈希；不放提示词、深链接、普通响应或命令行参数。终端模块复用已有输入、剪贴板、滚轮、渲染同步和几何竞态保护，隐藏显示不改变几何或发送输入。

## 验收证据与后续工作

本版本实现与测试覆盖：

- 准确原生身份事件、管理工具握手、没有工作终端时的只读初始化、错误和未知结果。
- 单默认管理者、稳定准备/启动/恢复键、自动工作列表、未来终端加入、legacy inactive 兼容和暂时断开的原对象保留。
- 管理身份与递归保护、关闭/历史对象排除、独立送达身份、明确新建目录边界及旧未提交请求的无重放迁移。
- 独立管理终端、无焦点抢夺、worker 草稿保留、滚轮不发送按键、剪贴板与几何保护。
- 桌面链接准确 ID、明确空闲确认、未核验状态、Hub 输入暂停与原会话恢复语义。

**仍需具体环境实机验证**：本机日常 Codex 安装与供应商、真实初始化完成/信任流程、准确原会话恢复、桌面加载同一工具身份和输入所有权、异常中断后的长期恢复。不能从 stub、假 PID 或打开 URL 推断这些验证完成。实机初始化 smoke 只调用管理身份自检，不读取或操作真实工作对象，不以业务任务充当初始化验证；测试须使用隔离 runtime，不再依赖“零 worker grant”构造隔离。

后续优先完成已验证桌面交接；再考虑桌面直接创建、多个管理入口的并发协调、更多任务看板和用户明确授权的自动跟进。不要先重造聊天模型后端，也不默认增加后台推理或定时调度。
